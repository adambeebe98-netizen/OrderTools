# Technician Supply Request Portal

A mobile-first web app for field technicians to request consumable supplies, and for managers to turn those requests into Grainger orders.

- **Technicians**: open the team link, type their name once, pick supplies, and submit. No account or password. Takes about 30 seconds.
- **Managers**: sign in to see requests, a **consolidated shopping list** (by product or by technician), mark items ordered (including partial orders), and manage the catalog.

Stack: Next.js 15 (App Router, TypeScript), Tailwind CSS v4, Radix/shadcn-style components, Supabase (Postgres + RLS, Auth, Storage), Web Push (VAPID), deployable on Vercel.

See [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) for the design decisions, schema and screens.

## Features

| Area | What's included |
| --- | --- |
| Technician | Name remembered on the device · search-first catalog with category chips · big − / + steppers · "Other item" (name, qty, why, link) · review and note · success screen · cart survives reloads and lost signal · "My requests" history with Requested / Ordered (and partial progress) · installable PWA that opens straight to their team |
| Dashboard | Outstanding requests · technicians waiting (oldest first) · new since last visit · recently ordered batches · recent activity |
| Requests | Filter by status/technician, search items or names, sort by date, pagination, multi-select → mark ordered · detail view: edit quantities, rename "other" items, remove/restore items, mark individual items ordered, undo |
| Shopping list | Consolidated by product (total, # technicians, per-technician breakdown, SKU, Grainger link) or grouped by technician · choose which requests go in the batch · uncheck individual lines (partial fulfillment) · copy as text, Grainger quick-order (`SKU,qty`), or CSV · mark selected ordered with an optional Grainger order # |
| Catalog | Add/edit/archive items · categories (add, rename, reorder, archive) · image upload or URL · units, descriptions, SKUs, URLs · CSV bulk import (upserts by SKU or name) · review frequent "other" requests and convert them into products (past requests are linked automatically) |
| Teams | Team-specific links (rotatable) · managers see only their team (enforced by Postgres RLS) · super admin manages teams, managers, super admins · technician rename/merge/archive |
| Notifications | Web Push to opted-in managers on new requests; clicking opens the request · per-device opt-in, per-team toggle, test button · in-app bell badge (polled) works without push |
| Hardening | Rate limits (per hashed IP + per team) on submissions, history lookups and sign-in · honeypot · strict Zod validation + DB constraints · composite FKs prevent cross-team references · `anon` role has no table access · security headers · CSV formula-injection protection |

Out of scope by design: purchasing automation, inventory, shipping/delivery tracking, approvals, technician accounts.

## Run locally

Prerequisites: Node 20+, Docker (for the local Supabase stack).

```bash
npm install
npm run db:start          # starts local Supabase (first run downloads images)
npm run db:reset          # applies migrations + seed data
cp .env.example .env.local
```

Fill `.env.local` with the values printed by `npx supabase status` (API URL, anon key, service_role key), then:

```bash
npx web-push generate-vapid-keys   # paste into NEXT_PUBLIC_VAPID_PUBLIC_KEY / VAPID_PRIVATE_KEY
npm run dev
```

- Technician page: <http://localhost:3000/r/north-install-demo>
- Manager sign-in: <http://localhost:3000/admin>. Use `manager@example.com` / `password123` (super admin, North team) or `other@example.com` / `password123` (South team only).

Seed data (`supabase/seed.sql`) is generated by `scripts/gen-seed.py`. The SKUs (`DEMO-…`) are placeholders. Grainger links point to search pages.

> The service worker only registers in production builds (or in dev with `?sw=1`). Push needs HTTPS in production; `localhost` is allowed for testing.

### Tests

```bash
npm test            # unit tests + database integration tests (RLS, ordering logic, rate limiter)
npm run test:e2e    # Playwright: technician submit → partial order → technician sees status
npm run lint && npm run typecheck
```

Database tests run against the local Supabase stack and are skipped when it isn't running. E2E tests need `npm run db:reset` seed data and start the dev server automatically.

## Deploy (Supabase + Vercel)

### 1. Supabase project

1. Create a project at <https://supabase.com>.
2. Apply the schema:
   ```bash
   npx supabase link --project-ref <your-project-ref>
   npx supabase db push            # applies supabase/migrations (NOT the seed)
   ```
3. **Authentication → Sign In / Providers**: keep Email enabled and **turn off "Allow new users to sign up"**. Managers are added by a super admin. Any account created another way still sees nothing without a team membership.
4. **Authentication → URL Configuration**: set Site URL to your production URL, and add `https://<your-domain>/admin/auth/confirm` to Redirect URLs (used by invite and password-reset emails).
5. Optional: configure custom SMTP (Auth → Emails) if you want invite/reset emails beyond Supabase's low default limits. Without email, add managers with a temporary password from the super admin page.

### 2. Vercel

1. Import the repository in Vercel (framework: Next.js).
2. Set environment variables (Production and Preview):

   | Variable | Value |
   | --- | --- |
   | `NEXT_PUBLIC_SUPABASE_URL` | Project URL |
   | `NEXT_PUBLIC_SUPABASE_ANON_KEY` | anon / publishable key |
   | `SUPABASE_SERVICE_ROLE_KEY` | service_role / secret key (**server only**) |
   | `NEXT_PUBLIC_SITE_URL` | `https://your-domain` |
   | `RATE_LIMIT_SALT` | random string (`openssl rand -hex 32`) |
   | `NEXT_PUBLIC_VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` | from `npx web-push generate-vapid-keys` |
   | `VAPID_SUBJECT` | `mailto:you@yourcompany.com` |

3. Deploy.

### 3. Create the first admin and team

**No command line:** in Supabase, go to Authentication → Users → Add user (tick *Auto Confirm User*). Then open the SQL Editor, paste [`supabase/setup-first-admin.sql`](supabase/setup-first-admin.sql), change the email and team name at the top, and click Run. (If you didn't use `supabase db push`, first paste and run `supabase/migrations/20261121000000_init.sql` the same way.)

**Or with the script:**

```bash
node --env-file=.env.production.local node_modules/.bin/tsx scripts/bootstrap.mts \
  --email you@company.com --password 'a-long-password' --name "Your Name" --team "North Install Team"
```

(`.env.production.local` needs `NEXT_PUBLIC_SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `NEXT_PUBLIC_SITE_URL`.) The script prints the technician link and dashboard URL.

### 4. Load your catalog

Sign in → **Catalog → CSV import**. Columns: `name`, `category`, `group`, `options`, `icon`, `unit`, `description`, `grainger_sku`, `grainger_url`, `image_url` (and `id` from an export). See [`docs/sample-catalog.csv`](docs/sample-catalog.csv).

- Simple products: fill `name` (and optionally `icon`).
- Products with variants: fill `group` and `options`, e.g. `group = Long Bit`, `options = Type: Masonry | Size: 3/8"`. The name is generated (`Long Bit — Masonry — 3/8"`). Each row is its own purchasable item with its own SKU.
- Re-importing updates in place, matching by `id`, then group + options, then SKU, then name — so IDs and SKUs are preserved and duplicates aren't created. **Export current catalog** produces a file in the same format.

### Product groups & variants

A *product group* (e.g. "Long Bit") is one card for technicians; tapping it opens a sheet where they pick each option (Type → Size), set a quantity and add. Options with a single choice are pre-selected. Each variant is a separate catalog row, so requests, the shopping list and Grainger SKUs always identify the exact variant. Managers create groups, variants, icons and the display order under **Catalog → Products**. Items that have been requested can be archived (hidden) but not deleted, so history stays accurate.

The one-time reorganization of the original flat drill-bit list lives in [`supabase/catalog-reorganize.sql`](supabase/catalog-reorganize.sql) (generated from `scripts/catalog_def.py`); it only renames/groups/archives items and verifies request data is unchanged.

### 5. Roll out

**Settings → Team request link**: copy the link or show the QR code, and text it to technicians once. On Android they can "Install app"; on iPhone, Share → Add to Home Screen. Managers turn on push in **Settings → Notifications** on each device. (iPhone requires the dashboard to be added to the Home Screen first, iOS 16.4+.)

## Security notes

- **Technician identity is not authentication.** Anyone with a team link can submit requests and view history for a name. The history page therefore shows only item names, quantities, dates, statuses and the technician's own note, from the last 120 days. No addresses, phone numbers or roster are collected or exposed. If a link leaks, rotate it in Settings.
- Manager data access uses the signed-in user's session, so Postgres Row Level Security enforces team isolation on every query. The service-role key is used only in server code for public team-link endpoints (scoped by slug), push fan-out, image upload after an access check, and super-admin pages.
- Raw IP addresses are never stored. Rate-limit keys use a salted SHA-256 hash.

## Project layout

```
src/app/r/[slug]/           technician pages (catalog, history, per-team manifest)
src/app/api/r/[slug]/       public submit + history endpoints (validated, rate limited)
src/app/admin/              manager pages (login, dashboard, requests, shopping list, catalog, …)
src/lib/consolidate.ts      shopping-list aggregation + exports (pure, unit tested)
src/lib/actions/            server actions (all re-check team access)
supabase/migrations/        schema, RLS policies, triggers, RPCs
public/sw.js                service worker (push + offline page)
tests/                      unit, database and e2e tests
```
